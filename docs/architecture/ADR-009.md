# ADR-009: validateFile / promote error separation

Status: Accepted

## Context

“Provably wrong content” (UNUSABLE → delete offending file) and “could not determine” (filesystem failure → FATAL → touch nothing) are different. Returning only an `outcome` would force callers to treat a transient `Stat`/`Open` error like bad content and risk deleting a resumable `.part` (the old `downloadFile` os.Remove-on-error reflex).

## Decision

`validateFile` returns `(outcome, error)`. A non-nil error means a filesystem failure mapped to FATAL with no deletion. UNUSABLE/INCOMPLETE/Done are content verdicts. `promote` returns an error on rename failure; callers map that to FATAL. Sibling cleanup after a successful rename is separate (ADR-013).

## Consequences

- Transient EACCES cannot destroy a resumable partial.
- Callers can distinguish content rejection from I/O failure without heuristics.
