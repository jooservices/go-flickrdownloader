# ADR-015: Persisted rolling API quota

Status: Accepted

## Context

Flickr caps REST API usage at 3600 requests per hour per API key, on top of the ~1 req/sec pacing the tool already applied. The per-process limiter (`golang.org/x/time/rate`) resets on every run, so two runs within the same hour could collectively exceed the hourly cap and hit Flickr's rate-limit error mid-run. The hourly quota is not visible to the user, and there is no way to know how many requests a planned job will consume against the remaining budget.

## Decision

A new `pkg/quota` package tracks a **rolling 1-hour window** of request timestamps, persisted per API key in an append-only log (`~/.config/flickrdownloader/quota-<sha256(apiKey)[:4]>.log`), one Unix epoch second per line.

- `Tracker.Wait` gates every REST call: it enforces the per-request interval, records the request, and when the window holds `hourlyLimit` entries it sleeps until the oldest entry expires (ctx-cancellable).
- Writes are **append-only and written through immediately** on each accepted request; see [ADR-016](ADR-016.md) for why (an earlier batched-write design left concurrent runs unable to see each other's usage). A torn trailing line is ignored on load. The file is rewritten (temp + atomic rename) only at load time when > 10 000 stale lines accumulate.
- The API client swaps its internal limiter for a `RateLimiter` interface (`SetRateLimiter`); the default limiter is unchanged when no tracker is installed. The client exposes `RequestCount`, `Quota` and `QuotaWaiting` for the UI.
- The UI surfaces: hourly usage in the run header and the `quota` command, a live `quota full — next slot in …` countdown in the progress bar while blocked, an API-cost estimate vs remaining budget in the plan/dry-run printout, and a final `API calls this run` summary.

## Consequences

- Separate runs in the same hour share the budget; the tool pauses instead of failing at the cap. This is enforced across processes via the interprocess lock in [ADR-016](ADR-016.md) — without it, each process only ever saw the snapshot it loaded at startup, so concurrent runs could collectively exceed the cap.
- Usage is keyed by API key, so a key shared with other applications is still over-counted locally — the tracking is best-effort and cannot see requests made outside this tool. A user can lower `api_hourly_limit` to compensate.
- The rolling window is the strictest reasonable interpretation; Flickr's enforcement may differ, but the tracker can only under-admit.
- `auth`'s OAuth token calls (`/services/oauth/*`) are not REST API calls and are exempt.
- Persistence adds one small file open/append/close per accepted request (~a few ms), paced by the ~1 req/sec interval already applied — negligible overhead, and it means no crash can undercount usage: nothing is held unflushed between requests (see ADR-016).
