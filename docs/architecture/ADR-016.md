# ADR-016: Interprocess quota lock

Status: Accepted

## Context

ADR-015's `Tracker` was designed so "separate runs share the same hourly budget," but the implementation didn't actually enforce that across processes: `New` loaded the on-disk log once at startup into an in-memory slice, and every later `Wait` call only ever consulted that in-memory copy, batching its own writes and never re-reading what a sibling process had appended. Two runs against the same API key (a manual run plus a cron job, or two terminals) each believed they had the full `hourlyLimit` budget to themselves. Their combined usage could exceed Flickr's 3600/hour cap — the exact failure the persisted tracker existed to prevent.

## Decision

`Tracker` now coordinates through an OS-level advisory file lock (`github.com/gofrs/flock`) on a sibling `<path>.lock` file:

- Every accept/deny decision (`tryRecord`) acquires the flock, **re-reads the shared log from disk**, trims it to the rolling window, and only then checks it against `hourlyLimit`. This replaces the old design's single in-memory snapshot with the authoritative combined state of every process sharing the path.
- An accepted request is **written through to the log immediately**, still holding the lock, before it's released — not batched. Since nothing is ever left unflushed between requests, the next `tryRecord` (by this process or another) is guaranteed to see it.
- The lock is only held for the read-check-append-flush sequence, then released before any sleep; a process blocked on the hourly cap doesn't hold the lock while waiting, so it can't starve others out of checking their own state.
- flock is scoped to the holding process's lifetime — the OS releases it automatically on exit or crash, so there's no stale-lock file to detect or clean up, unlike a PID-file-based lock.
- `path == ""` (no persistence, e.g. some tests) skips the lock entirely and falls back to the original in-memory-only trim, since there's no shared file to coordinate over.

## Consequences

- Correctness now holds under concurrent processes, not just concurrent goroutines within one process — this was previously assumed but unverified. See the `TestInterprocessSharedBudget` regression test in `pkg/quota/quota_test.go`.
- The previous 60-request write batching (and its "loses at most 60 unrecorded requests" trade-off) is gone; every accepted request incurs one small file open/append/close, cheap next to the ~1 req/sec pacing already applied.
- `Flush()` is now mostly a no-op safety net rather than a required call on exit, since `Wait` never leaves anything unflushed — kept for callers that mutate entries outside `Wait`.
- Lock acquisition polls (`TryLockContext`, 25ms retry) rather than using a native blocking `Lock()`, so it stays `ctx`-cancellable — a user hitting Ctrl-C while a sibling process holds the lock doesn't hang.
