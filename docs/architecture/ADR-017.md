# ADR-017: Release checksum verification on self-update

Status: Accepted

## Context

`flickrdownloader update` downloads a release archive over HTTPS and installs it over the currently running binary. The only integrity check was a byte-length comparison against the `size` field GitHub's release API reports for the asset — a check an attacker who controls the asset content (a compromised release, a substituted mirror, or a MITM that also forges the size field) can trivially satisfy. There was no cryptographic verification that the downloaded bytes were what was actually published.

## Decision

`Install` now refuses to install unless it can verify the downloaded archive's SHA-256 against a source independent of the raw download itself:

1. **Preferred: GitHub's asset `digest` field.** GitHub computes a `sha256:<hex>` digest server-side for uploaded release assets and returns it in the release API response. Since this comes from a separate API response rather than the asset download itself, an attacker able to tamper with the CDN-served asset bytes (or a mirror, or a MITM on that one connection) would also have to forge the `api.github.com` response to pass verification.
2. **Fallback: a detached checksums file.** If an asset has no `digest` (e.g. it predates GitHub adding that field), `Install` looks for a sibling checksums asset (`checksums.txt`, `SHA256SUMS[.txt]`, or `*_checksums.txt` — the goreleaser convention) in the same release and verifies against the matching line.
3. **Neither available → refuse to install.** A byte-length-only check is not a meaningful integrity guarantee, so silently falling back to it would defeat the point; `Install` returns an error telling the user to install manually instead.

## Consequences

- Self-update no longer trusts a value (`Size`) that's exactly as attacker-controlled as the payload it's supposed to check.
- This does not protect against a fully compromised GitHub account that also rewrites the API's digest/checksums response — that would require out-of-band signing (e.g. cosign, GPG-signed checksums) on the release-publishing side, which is out of scope for the client alone.
- Existing releases published before this change, with neither a `digest` nor a checksums asset, can no longer be self-updated to (or from) — users on such a release must upgrade manually once, after which future releases (which do carry a GitHub-computed digest automatically) update normally.
