# ADR-019: Account-scoped SQLite response cache

Status: Accepted

## Context

Every run re-fetched the same Flickr REST responses: photoset listings, photo details, and size lookups were requested from scratch regardless of how recently they had been fetched, and regardless of how much the previous run had already learned. With the ~1 req/sec REST limiter and the 3600/hour cap, re-listing a large photostream or re-verifying existing albums spent the entire budget on metadata that had not changed. There was also no way to work offline — a quota-saturated hour, a network outage, or a throttled key made the tool unusable even for local validation.

## Decision

A new `pkg/cache` package persists successful Flickr REST responses in a per-account SQLite database, exposed to `pkg/api` through a small consumer-defined `ResponseCache` interface (accept-interfaces-return-structs: test doubles and the real store both implement it).

- The database lives at `~/.config/flickrdownloader/cache-<sha256(apiKey+NSID)[:8]>.db`, one connection, `journal_mode=WAL`, `synchronous=NORMAL`, file mode `0600`.
- Responses are keyed by an account-scoped request key (`SetCacheNamespace`). Cached bodies are stored verbatim; freshness is tracked with `fetched_at` and a per-method TTL: listings (getPhotos/getPhotosets/getPhotosetInfo/getNotInSet) default to 24h, details/sizes to 30 days.
- `--refresh` bypasses existing entries; `--offline` (cache-only) never issues a REST request and reports an explicit miss. Cache failures are non-fatal in normal mode so a damaged database cannot block a download.
- Schema is versioned (currently 7) and migrated forward on open; a database from a newer binary is refused rather than corrupted.
- A `cache prune`/`cache clear` command pair exposes retention and full reset to the user.

## Consequences

- Repeated and re-run downloads stop spending the hourly quota on unchanged metadata; cache hits are reported and excluded from the API-cost summary.
- The cache is an optimization, never a correctness dependency: normal-mode callers fall back to the network on any cache error.
- Choosing pure-Go `modernc.org/sqlite` keeps the build cgo-free, so GoReleaser can cross-compile all targets with `CGO_ENABLED=0`.
- A single `sql.DB` connection keeps SQLite locking predictable (WAL + one writer); REST requests are already rate-limited to ~1/sec, so this is not a throughput bottleneck.
