# ADR-020: Auth-fingerprint cache binding

Status: Accepted

## Context

The response cache is stored on the local machine and can outlive a session. If the user re-authenticates (`flickrdownloader auth` again, or a token rotation), the previous account's private listing responses would otherwise remain in the same cache database. A later run under the new credentials could then read and re-use metadata that belongs to a different Flickr account — leaking which photosets/photos exist in someone else's private photostream.

## Decision

Each cache database is bound to the current OAuth access token via a **non-secret SHA-256 fingerprint** stored in a `cache_meta` table:

- `cache.Open` + `BindAuth` are called together on startup. If the stored fingerprint matches the current token, the cache is used as-is.
- If it differs, the database's REST responses, normalized photo metadata, and response leases are deleted in one transaction before the new fingerprint is stored. Photoset completion manifests are **retained** because they describe local files on disk, not remote API state.
- The cache filename already includes a hash of `apiKey+NSID`, so a credential switch also lands in a fresh database; the fingerprint bind is a second, independent layer that survives path reuse.

## Consequences

- A changed credential cannot accidentally reuse another session's private listings.
- The fingerprint is a hash of the access token but is not a secret itself (it is not usable to make requests), so storing it in the same directory as the token adds no meaningful disclosure risk.
- Re-authentication invalidates the REST cache once — subsequent runs keep their cache until the next credential change, which is the intended trade-off between privacy and cache lifetime.
