# ADR-022: Coordinating cache misses across goroutines and processes

Status: Accepted

## Context

A cache miss for a listing page is expensive: it costs a REST request under the 3600/hour cap. Two concurrent runs (a manual run and a cron job, or two terminals against the same account) could miss the same key at the same moment and each spend a request fetching identical metadata. Even within one run, parallel workers could request the same photo detail twice before either result lands in the cache. The existing quota tracker already coordinates *budget* across processes, but not *duplicate work*.

## Decision

Two complementary mechanisms, layered:

1. **In-process singleflight** (`golang.org/x/sync/singleflight`) on the API client: concurrent callers for the same request key coalesce onto one REST fetch, and all waiters receive the single result. This collapses parallel duplicate misses inside a run.
2. **Cross-process response leases** in SQLite: before issuing a REST request on a cache miss, the client inserts a lease row (`cache_key`, owner, `expires_at`, 2-minute TTL, renewed every 40s). If the insert claims the key, the owner performs the fetch and populates the cache; everyone else polls briefly and reads the newly-written cache entry instead of issuing their own request. Expired leases can be re-claimed, so a crashed owner does not deadlock other processes.

## Consequences

- A popular cache key is fetched once per process *and* once across concurrently running processes; duplicate REST spending on misses is eliminated in the common case.
- The lease TTL/renewal bounds worst-case waiting: a dead owner's lease expires within 2 minutes and other runs proceed.
- The mechanisms are optional capability interfaces (`responseCacheLease`) type-asserted at the call site, so test doubles and in-memory caches are not forced to implement them.
- This is best-effort coordination, not a lock: the REST cache is still only an optimization, and correctness never depends on two processes agreeing on who fetches.
