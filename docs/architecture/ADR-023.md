# ADR-023: Output-root locking and recursive local reuse

Status: Accepted

## Context

Two problems appeared once caching made concurrent runs practical. First, ADR-003/BR8's stale-`.part` sweep and the cross-album dedupe/hardlink map assume a single writer owns a photo ID per run; two CLI instances writing into the same output tree could race the same photo ID, delete each other's `.cand`, or sweep in-progress files. Second, a re-run against an account that was already downloaded should not re-download or even re-resolve anything — but the previous local tree was only used to skip identical final paths, not to reuse files across albums or detect completeness.

## Decision

1. **Output-root lock.** Before any run that writes to an output tree, the CLI acquires an exclusive advisory lock (`gofrs/flock`) on `<canonical-output-root>.flickrdownloader.lock`. `CanonicalPath` resolves symlinks first so two spellings of the same path serialize. Concurrent CLI instances using the same tree are serialized; different output roots (and the API quota and response cache) remain shared.
2. **Recursive local index.** `indexLocalFiles` walks an owner tree once at the start of a run and seeds the cross-album dedupe map (`photoID → path`) with every complete file found, keyed per directory. The filesystem remains the source of truth; the index is an in-memory optimization for the current run.
3. **Local reuse instead of re-download.** When a photo is already present locally, later albums reuse it via a hardlink (`os.Link`) with a local copy as the fallback for cross-filesystem output trees — no `getSizes`, no CDN request, no `--workers` slot.

## Consequences

- The old "concurrent CLI instances on one tree are unsupported" limitation is removed; serialized execution makes the sweep and dedupe invariants safe again.
- Re-runs reuse files across albums and skip listing pages for fully-present photosets (ADR-021), cutting both API requests and CDN traffic to near zero for unchanged accounts.
- The lock is advisory and per-tree: it deliberately does not serialize runs with different output roots, and it does not lock the network-shared quota/cache.
- A hardlink requires the source and target on the same filesystem; the copy fallback keeps reuse working across mounts at the cost of duplicating bytes.
